## 概要（公開される想定）

「たまに落ちるテスト」「本番でだけ起きるレースコンディション」——並行処理のバグは再現が難しく、私たちはしばしばその検証を諦めてしまいます。何度リトライしても再現せず、「とりあえずリランしたら通った」で流してしまった経験はないでしょうか。

JetBrains製のテストフレームワークLincheckは、この難問に「スレッドのインターリービング（実行順序の組み合わせ）を系統的に探索する」というアプローチで挑んでおり、kotlinx.coroutines自体の品質保証にも使われています。

本セッションでは、Lincheckの使い方を入り口に、その背後にある考え方を紐解きます。

- 並行コードの「正しさ」をそもそもどう定義するか（線形化可能性）
- 非決定性を運任せにせず、制御下に置くにはどうするか（ストレステストとモデルチェッキング）
- suspend関数を含む並行コードの正しさをどう検証するか——coroutinesを持つKotlinだからこそ生まれたアプローチ
- 「どうテストするか」ではなく「何をテストするか」を書く宣言的テスト

聴講後には、Lincheckというツールの使い方だけでなく、並行処理と向き合うための思考の道具を持ち帰っていただけます。

## セッション詳細（審査用）

### 背景・モチベーション

並行処理のバグは「再現しない」という一点において、通常のバグと質的に異なります。多くの開発者はこれを「flakyなテスト」として無効化したり、リトライで握りつぶしたりしており、体系的にテストする方法が知られていません。KotlinコミュニティにはJetBrains自身がkotlinx.coroutinesのテストに使うLincheckという強力な答えがあるにもかかわらず、日本ではほとんど紹介されていません（Kotlin Festでの登壇実績なし。KotlinConf 2023でJetBrainsによるワークショップがあるのみ）。

### 構成（20分）

1. **つかみ（2分）**: 再現しない並行バグ、諦めていませんか——2スレッドでカウンタをインクリメントするだけの「正しく見える」コードを提示
2. **なぜ再現しないのか（3分）**: インターリービングの組み合わせ爆発。通常のテストが無力な理由
3. **Lincheckのアプローチ（7分）**:
   - そもそも「正しい」とは何か——線形化可能性という正しさの定義（JCStressの「結果の列挙」方式との対比でsequential specificationの考え方を示す）
   - 2つの戦略の対比: ストレステスト（確率に賭ける）とモデルチェッキング（スケジューリングを制御して探索する）
   - suspend関数もテストできる——線形化可能性をサスペンドする操作へ拡張し、Channelのsend/receiveのような操作を検証。kotlinx.coroutines自体がこの仕組みでテストされている
4. **実演（5分）**: 冒頭のバグをLincheckで確実に再現し、失敗トレース（どのインターリービングで壊れたか）を読み解く
5. **持ち帰り（3分）**: 並行処理に向き合う3つの考え方——①正しさの定義から始める、②非決定性を祈りではなく探索で扱う、③「何を」テストするかを宣言する

### 新規性・Kotlin独自の知見

**① Kotlinを支えている実績あるツールである**

- LincheckはJetBrains製で、kotlinx.coroutinesの開発プロセスに組み込まれ、Mutex・Semaphore・Channelといったcoroutinesプリミティブの品質保証に実際に使われている（CAV 2023採録論文で報告）
- kotlinx.coroutinesだけでなくJCToolsなど著名な並行ライブラリで実際に未知のバグを発見した実績がある
- 「Kotlinの中核ライブラリが、どうやって自分自身の並行性を検証しているか」という視点自体がKotlin独自の知見になる

**② suspend関数をテストできる——coroutinesを持つKotlinだから必要になった技術**

- JVMの類似ツールJCStressは「起こりうる実行結果を人間が列挙する」方式で、suspend関数は扱えない
- Lincheckは線形化可能性をサスペンドする操作に拡張し（dual data structuresの理論）、Channelのsend/receiveのように「サスペンドすることこそが正しい挙動」である操作を検証できる
- これはcoroutinesという言語機能を持つKotlinだからこそ生まれた技術であり、「Kotlin独自の知見」の核として最も強く打ち出せるポイント

**③ 正しさを「列挙」ではなく「仕様」で語る**

- JCStressが結果の列挙を要求するのに対し、Lincheckはsequential specification（逐次実行した場合と等価な結果か）で正しさを自動判定する
- 「並行コードの正しさは逐次的な仕様との等価性で定義する」という考え方の転換を、両者の対比で具体的に見せられる

**④ 2026年に話すタイミングとしての新規性**

- Lincheck 3（最新3.6、2026年5月リリース）でパッケージが`org.jetbrains.lincheck`に移行し、`Lincheck.runConcurrentTest`による任意の並行コードのテストへと守備範囲が拡大。「並行データ構造の作者のためのツール」から「一般開発者のツール」へ進化した転換点にある
- IntelliJ IDEAでの失敗トレースのステップ実行デバッグ統合など、実務導入の敷居が下がった今こそ紹介する価値がある
- 日本語でのLincheck解説はほぼ存在せず、Kotlin Festでの登壇実績もない（KotlinConf 2023でのJetBrains自身によるワークショップ・講演のみ）

**セッションへの反映**: ②と③は本編の「Lincheckのアプローチ」パートで、①と④は導入と締めで触れる。単なるツール紹介に留めず、線形化可能性・モデルチェッキングという計算機科学の概念を、Kotlinコードと実演を通じて中級者に届く形に翻訳する点が本セッションの独自性。
