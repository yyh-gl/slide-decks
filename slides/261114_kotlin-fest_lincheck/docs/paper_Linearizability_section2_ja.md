# 2. システムモデルとLinearizabilityの定義

出典: M. Herlihy and J. Wing, "Linearizability: A Correctness Condition for Concurrent Objects", ACM TOPLAS, Vol. 12, No. 3, July 1990, pp. 466-470 の第2章の日本語訳。

## 2.1 履歴（Histories）

非形式的には、並行システムは、プロセス（process）と呼ばれる逐次的な制御スレッドの集まりで構成される。プロセスは、オブジェクト（object）と呼ばれる共有データ構造を介して通信する。各オブジェクトは一意の名前と型（type）を持つ。型は、取りうる値の集合と、そのオブジェクトを操作する唯一の手段である基本操作の集合を定義する。プロセスは逐次的である。各プロセスは、オブジェクトに対して一連の操作を適用し、呼び出し（invocation）の発行と、対応する応答（response）の受信を交互に繰り返す。（動的なプロセス生成は、子プロセスを、fork前とjoin後には何も操作を実行しない追加のプロセスとして扱うだけでモデル化できる。）

形式的には、並行システムの実行は履歴（history）でモデル化する。履歴とは、操作の呼び出しイベントと応答イベントからなる有限列である。履歴Hの部分履歴（subhistory）とは、Hのイベントの部分列である。操作の呼び出しは `(x op(args*) A)` と書く。ここで、xはオブジェクト名、opは操作名、args\*は引数値の列、Aはプロセス名である。操作の呼び出しに対する応答は `(x term(res*) A)` と書く。ここで、termは終了条件、res\*は結果の列である。正常終了には "Ok" を使う。応答が呼び出しに対応する（match する）のは、オブジェクト名とプロセス名がどちらも一致するときである。ある履歴において、対応する応答が後続しない呼び出しは保留中（pending）であるという。Hが履歴のとき、complete(H) は、Hのうち呼び出しとそれに対応する応答だけからなる最大の部分列とする。

履歴Hが逐次的（sequential）であるとは、次の条件を満たすことをいう。

1. Hの最初のイベントが呼び出しである。
2. 最後の呼び出しを除くすべての呼び出しの直後に、対応する応答が続く。また、すべての応答の直後に、対応する呼び出しが続く。

逐次的でない履歴は並行的（concurrent）であるという。

履歴Hのプロセス部分履歴（process subhistory）H | P（HのP視点）は、Hのイベントのうち、プロセス名がPであるものすべてからなる部分列である。オブジェクト部分履歴（object subhistory）H | x も、オブジェクトxについて同様に定義する。2つの履歴HとH'が等価（equivalent）であるとは、すべてのプロセスPについて H | P = H' | P が成り立つことをいう。履歴Hがwell-formedであるとは、Hの各プロセス部分履歴 H | P が逐次的であることをいう。本論文で扱う履歴はすべてwell-formedであると仮定する。well-formedな履歴のプロセス部分履歴は必ず逐次的になるが、オブジェクト部分履歴はそうとは限らない点に注意してほしい。

履歴における操作（operation）eは、呼び出し inv(e) と、それに続く最初の対応する応答 res(e) の対である。操作は `[q inv/res A]` と書く。ここで、qはオブジェクト、Aはプロセスである。履歴Hにおいて、操作 e0 が別の操作 e1 の内側にある（lies within）とは、Hにおいて inv(e1) が inv(e0) に先行し、かつ res(e0) が res(e1) に先行することをいう。山括弧（イベント）と角括弧（操作）は、かえって紛らわしくなる場合には省略する。文脈から明らかな場合は、オブジェクト名とプロセス名も省略する。

例として、図1のH1は、FIFOキューqに対する次のwell-formedな履歴である。

```
q Enq(x) A
q Enq(y) B
q Ok()   B
q Ok()   A
q Deq()  B
q Ok(x)  B
q Deq()  A
q Ok(y)  A
q Enq(z) A
```

H1の最初のイベントは、プロセスAによる引数xのEnqの呼び出しである。4番目のイベントは、終了条件がOkで結果なしの、対応する応答である。操作 `[q Enq(y)/Ok() B]` は、操作 `[q Enq(x)/Ok() A]` の内側にある。部分履歴 complete(H1) は、H1から最後の（保留中の）Enqの呼び出しを取り除いたものである。最初の2つのイベントを入れ替えると、H1と等価な多数の履歴のうちの1つが得られる。

履歴の集合Sが接頭辞閉（prefix-closed）であるとは、HがSに属するとき、Hのすべての接頭辞もSに属することをいう。単一オブジェクト履歴（single-object history）とは、すべてのイベントが同じオブジェクトに関係する履歴である。オブジェクトの逐次仕様（sequential specification）とは、そのオブジェクトに関する単一オブジェクト逐次履歴の、接頭辞閉な集合である。逐次履歴Hが正当（legal）であるとは、各オブジェクト部分履歴 H | x が、xの逐次仕様に属することをいう。逐次仕様を定義する従来の手法は数多くある。本論文ではLarch [19] の公理的なスタイルを用いる。このスタイルでは、オブジェクトの逐次履歴を1つの値で要約する。この値は、（非形式的にいえば）履歴の終了時点でのオブジェクトの状態を反映する。この値を使って、オブジェクトの各操作の事前条件と事後条件を与える公理を記述する。たとえば、FIFOキューのEnq操作とDeq操作の公理を図3に示す。Enqの事後条件は、終了時の新しいキューの値が、古いキューの値にeを挿入したものになることを述べている。Deqの仕様は、空でないキューにこの操作を適用すると、キューから先頭の要素が取り除かれることを述べている。操作が全域的（total）であるとは、Enqのように、オブジェクトのすべての値に対して定義されていることをいう。そうでない操作は部分的（partial）であるという。Deqは空のキューに対して未定義なので、部分的である。

> **図3 キュー操作の公理**（原文の図は抽出時に崩れていたため、論文の内容から復元）
>
> - 公理E: 事前条件なし。`Enq(e)/Ok()` の事後条件は `q' = ins(q, e)`
> - 公理D: 事前条件は `q` が空でないこと。`Deq()/Ok(e)` の事後条件は `q' = rest(q) ∧ e = first(q)`

## 2.2 Linearizabilityの定義

履歴Hは、操作に対する非反射的な半順序 <H を導く。

> e0 <H e1 ⟺ H において res(e0) が inv(e1) に先行する。

（適切な場合は、半順序の添字を省略する。）非形式的には、<H はHにおける操作の「実時間」での先行順序を表す。<H で関係づけられない操作は、並行（concurrent）であるという。Hが逐次的ならば、<H は全順序である。

--# 全順序: 簡単に言うと、集合内の任意の2つの要素が常に比較可能である（大小関係を一意に決定できる）ような順序構造のこと

履歴Hがlinearizableであるとは、Hに0個以上の応答イベントを追加して拡張した何らかの履歴H'で、次の条件を満たすものが存在することをいう。

- **L1:** complete(H') が、ある正当な逐次履歴Sと等価である。
- **L2:** <H ⊆ <S である。

非形式的には、Hを拡張してH'を考えるのは、応答がまだ呼び出し元に返っていなくても、一部の保留中の呼び出しがすでに効果を及ぼしている可能性があるという考えを捉えるためである（図1の履歴H1の保留中のEnqがその例である）。complete(H') だけに注目するのは、残りの保留中の呼び出しがまだ効果を及ぼしていないという考えを捉えるためである。L1は、プロセスが、完結した操作の粒度でインターリーブされたかのように振る舞うことを述べている。L2は、この見かけ上の逐次的なインターリーブが、操作の実時間での先行順序を尊重することを述べている。

Sを、Hのlinearization（線形化）と呼ぶ。linearizabilityには本質的に非決定性がある。(1) 各Hについて、2つの条件L1とL2を満たす拡張H'は複数ありうる。(2) 各拡張H'について、linearizationであるSは複数ありうる。linearizableなオブジェクトとは、その並行履歴が、ある逐次仕様に関してlinearizableであるオブジェクトである。

## 2.3 キューの例の再検討

"・" をイベントの連結とする。図1に示した履歴H1はlinearizableである。H1 ・ `(q Ok() A)` が、次の逐次履歴と等価だからである。

```
q Enq(x) A
q Ok()   A
q Enq(y) B
q Ok()   B
q Deq()  B
q Ok(x)  B
q Deq()  A
q Ok(y)  A
q Enq(z) A
q Ok()   A
```

H2はlinearizableではない。

```
q Enq(x) A
q Ok()   A
q Enq(y) B
q Deq()  A
q Ok()   B
q Ok(y)  A          （履歴H2）
```

完結したxのEnqがyのEnqに先行しているのに、xより先にyがデキューされているからである。

Linearizabilityは、H3のように、操作が戻りイベントの発生前に「効果を及ぼす」履歴を排除しない。

```
q Enq(x) A
q Deq()  B
q Ok(x)  B          （履歴H3）
```

H3は H3' = H3 ・ `(q Ok() A)` に拡張できる。H3'は、エンキューがデキューより前に起こる逐次履歴と等価である。

最後に、H4を考える。

```
q Enq(x) A
q Enq(y) B
q Ok()   A
q Ok()   B
q Deq()  A
q Deq()  C
q Ok(y)  A
q Ok(y)  C          （履歴H4）
```

H4はlinearizableではない。yが1回しかエンキューされていないのに2回デキューされており、H4はFIFOキューのどの逐次履歴とも等価にならないからである。

## 2.4 読解中の疑問と回答メモ（訳者追記）

2章を読む中で出た疑問と、その回答の整理。原文にはない内容である。

### Q1. 逐次履歴の条件(2)「各応答の直後に、対応する呼び出しが続く」はどう読むか

- 受動態なので、応答の後ろに続くのは呼び出しである。「各応答は対応する呼び出しの直後に続く」とは訳せない。そう訳すと1文目の言い換えになり、前後関係も逆になる。
- 2文目が付け加えているのは、「応答の次には呼び出しが来る」という条件である。これで呼び出しと応答が交互に並ぶ形に定まる。
- この"matching"は、オブジェクト名とプロセス名が一致するという意味で使われている。応答の直後の呼び出しは新しい操作のものなので、厳密な意味での「対応」ではない。論文の書き方が緩い箇所である。
- 履歴は有限列なので、最後のイベントが応答の場合、その直後に呼び出しは続かない。1文目の呼び出しには "except possibly the last" の例外があるが、2文目にはない。文字どおりに読むと、応答で終わる履歴が逐次履歴にならず、論文自身の例（2.3のS）と矛盾する。意図としては、2文目にも「最後は除く」が付くと読むのが自然である。

### Q2. complete(H1) と「最初の2つのイベントの入れ替え」は何をしているのか

H1の9番目のイベント `Enq(z) A` には応答がない（保留中）。complete(H1) は、これを取り除いたイベント1〜8である。

等価の定義は「すべてのプロセスPについて H | P = H' | P」なので、プロセスごとに見た列が同じなら等価である。別プロセスのイベントどうし（1番目の `Enq(x) A` と2番目の `Enq(y) B`）は、入れ替えても各プロセスの列が変わらない。よって、入れ替えた履歴はH1と等価である。3番目と4番目の入れ替えなど、同様の入れ替えが多数あるので "one of many" と書かれている。同じプロセスのイベントどうしを入れ替えると、プロセス部分履歴が変わるので等価にならない。

### Q3. 「呼び出しの直後に応答が続く」という逐次の条件は、H1でも満たす必要があるか

必要ない。この条件は逐次履歴の定義の一部で、H1のような並行履歴には課されない。H1に求められるのはwell-formedであること、つまり各プロセス部分履歴が逐次的であることだけである。H1 | A も H1 | B も、呼び出しと応答が交互に並んでおり、この条件を満たす。

### Q4. 2.3でH1がlinearizableである理由と、`(q Ok() A)` を連結する理由

- linearizableの定義は「条件L1・L2を満たすH'とSが存在する」ことである。論文は、H' = H1 ・ `(q Ok() A)` と、それと等価な逐次履歴Sを示している。これは存在の証明の具体例にあたる。
- H1の最後の `Enq(z) A` は保留中である。応答を補って効果が出たと見なしても、補わずに効果が出ていないと見なしても、定義上は許される。論文は前者を選んで、拡張の例を見せている。後者でも、Sの末尾の `Enq(z)` を除いた4操作でH1はlinearizableになる。連結は必須の手順ではない。
- Sが呼び出しと応答のペアで連続して並ぶのは、逐次履歴だからである。この形でないと、図3のような事前条件・事後条件で、各操作の前後の状態を1つずつ確かめられない。

### Q5. L2（<H ⊆ <S）は何を言っているか

Hで「終わってから始まった」操作の順番は、Sでも逆転させない、という条件である。並行だった操作は、Sでどちらの順に並べてもよい。

- H1では、`Enq(x) A` と `Enq(y) B` は並行なので、L2からはどちらが先でもよい。しかし `Deq B` が x を返しているので、y を先に入れると正当にならない。L2が許す並びの中から、L1が正しいものを選ぶ分担になっている。
- H2では、`Enq(x)` が `Enq(y)` に先行する（`Enq(x)` の応答が `Enq(y)` の呼び出しより前にある）。L2により、Sでも x, y の順になる。すると `Deq` は x を返すはずだが、Hでは y を返しているため、正当なSが存在しない。L2がなければ、y, x の順のSが取れてしまう。
- L1だけでは実時間の順序が無視される。L2がそれを尊重させる。

### Q6. 線形化可能性を証明するには、線形化できないケースを見つける必要があるか

逆である。

| | 示したいこと | 必要なこと |
|---|---|---|
| 1つの履歴H | Hが線形化可能 | 条件を満たすH'とSを1組見つける（存在の証明） |
| 1つの履歴H | Hが線形化不可能 | 条件を満たす組が1つも存在しないことを示す |
| オブジェクト全体 | 線形化可能 | すべての履歴が線形化可能であることを示す |
| オブジェクト全体 | 線形化可能でない | 線形化不可能な履歴を1つ見つける（反例） |

### Q7. Lincheckのテストをパスしても、線形化できないケースが隠れていることはあるか

ある。Lincheckがやっているのは反例探しで、パスしても「探索した範囲では見つからなかった」ことしか言えない。探索の範囲が限られる要因は次のとおりである。

- シナリオの範囲: 操作の組み合わせ、スレッド数、各スレッドの操作数に上限がある。
- スケジューリングの範囲: ストレステストモードは実行のタイミング任せで、まれなインターリーブは出ないことがある。モデル検査モードも、探索の深さや量に制限がある。

失敗した場合は、線形化不可能な履歴が実際に見つかった確実な証拠である。パスした場合は、バグの不在の証明にはならない。なお、モデル検査モードの網羅の範囲は、公式ドキュメントで確認すること。

### Q8. 「linearizabilityには本質的に非決定性がある」の非決定性はどこにあるか

乱数的な意味ではなく、HからSへの対応が一意に決まらない（選択肢が複数ある）という意味である。論文が挙げる2か所は次のとおり。

1. 拡張H'の選び方: 保留中の呼び出しに、応答を補うか補わないか（補う場合は結果の値も）を選べる。H1の `Enq(z) A` がその例である。
2. H'に対するSの選び方: 並行な操作は、Sでどちらの順に並べてもよい。例として、`Enq(x) A`、`Enq(y) B`、`Ok() A`、`Ok() B` の履歴では、x, y の順も y, x の順も正当なSになる。

判定は「条件を満たすH'とSが存在するか」という存在の問題であり、関数のように答えが1つに決まるわけではない。

### Q9. この非決定性は、Lincheckで確認しきれない話と関係があるか

ほぼ無関係である。層が違う。

- 論文の非決定性は、すでに得られた1つの履歴を判定するときの話である。候補は有限なので、全部試して確定的に答えが出る。起こりうるのは計算コストの問題だけである。
- 見逃しは、どの履歴を観測できるかの話である。同じプログラムでも、スレッドのタイミングで生じる履歴が毎回違う。この実行の非決定性が原因で、起こりうる履歴の一部しか観測できない。

### Q10. 「処理がある1点で瞬時に起きる」という説明は、論文でどう言及されているか

直観の説明として、明示的に書かれている。

- アブストラクト: 各操作が、呼び出しから応答までの間のどこかの時点で、瞬時に効果を及ぼしたかのような錯覚を与える（"takes effect instantaneously at some point between its invocation and its response"）。
- 1.2 Motivation: 正しさの条件として直観的に妥当な要件は2つある。各操作は瞬時に「効果を及ぼす」ように見えること、並行でない操作の順序が保たれることである。
- 6章（関連研究）: アブストラクトとほぼ同じ文に続けて、1点で起きると見なせれば、操作の意味を事前条件・事後条件で与えられることが利点だと述べている。

形式的な定義（2章）に「1点」「瞬時」という語は出てこない。対応は次のとおりである。

- 「瞬時に効果を及ぼす」は、L1（完結した操作の粒度でインターリーブされたかのような逐次履歴Sがある）に対応する。
- 「呼び出しと応答の間のどこか」は、L2（実時間で先行する操作の順序がSでも保たれる）に対応する。

なお、論文の4章では、各操作が実行ステップのどこか1点で効果を出すと見なす抽象関数の手法（Lamportの提案）を紹介している。論文のキューの実装は、この手法ではうまく扱えない例として挙げられている。そのため、「1点」が実装中の特定のステップとして特定できるとは限らない。
